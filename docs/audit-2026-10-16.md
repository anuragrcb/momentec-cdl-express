# CDL Express: end-to-end audit

Date: 16 October 2026
Scope: the Next.js app (`app/`, `lib/`), the proof Lambda (`lambda/src/`), the catalog search service (`Momentec_VectorEmbeddings/app/`), and the deployment notes (`docs/aws.md`, `scripts/create-aws-proof.sh`). I checked the code against `docs/how-it-works.html`, `README.md`, and the decisions in `mom/12-10-2026.md`.

This is a static read of the code. I did not run the app, call Gemini or Magnific, or open the AWS console. Findings that depend on live behaviour are marked **(verify)**.

---

## 1. Summary

The pipeline is built and works as a POC: Gemini describes the upload, catalog search proposes styles, Gemini picks a style and plans the design, Magnific paints the plan onto the Momentec template, and a Lambda builds the proof PDF. It is not production ready yet. The main problems fall into five groups:

1. **The form inputs never reach style matching.** Gender and category are locked until after the four views exist, so matching always runs without them (see 3.1). This is the most important correctness bug.
2. **Prompts return free text and the code parses it with regexes.** None of the Gemini calls use structured output, temperature, or retries. Placements and colors are filtered by matching substrings in prose, so wrong codes can get through and bad JSON either fails the job or quietly produces a junk search query.
3. **Each generation pass adds drift.** The customer photo is downscaled to 512 px. Magnific renders the sheet at `quality: "low"`. The Lambda then has Magnific redraw the front, the back, and every mark again from that sheet. The proof can differ from what the customer saw, and text is the first thing to break.
4. **Several MoM decisions are not built yet:** exact or PMS customer colors, real order data on the PDF, Comms integration, the proof-storage naming convention, and a path for "no confident match".
5. **Security and operations gaps.** The public routes spend Gemini and Magnific credits with no auth or rate limit. The server trusts the sheet and catalog JSON the client sends back. The catalog API is open if `API_KEY` is unset. `lambda/` and `Momentec_VectorEmbeddings/` are gitignored, so the production code is not under version control.

Section 7 has a prioritised fix plan.

## 3. Flow and correctness bugs

### 3.1 Gender and category never reach style matching (P0)
`UploadAiDesignModal.tsx:533` disables the whole `<fieldset>` while `fieldsLocked` is true, and `fieldsLocked` is true until all four views exist (`:393`). `requestSheet` sends `gender` and `category` only when they are set (`:221-222`), and they cannot be set before the first generate. The result:
- `searchCatalog` never gets a segment or sport filter from the form, so the segment always comes from Gemini's guess.
- The customer can choose **Women** after an **adult** cut was matched. The PDF then prints `WOMEN M` next to a men's template.
- `docs/how-it-works.html` step 1 says sport, gender, and size are sent "if the form already has them". The UI makes that impossible.

**Fix:** collect gender and category before generating, or re-run matching when they change. In the production flow (AI Creator form, section 6) every field is known at submit, so this goes away if matching moves into the backend job.

### 3.2 "Apply this edit" drops the catalog template (P0)
With an instruction set, `generateMissingSheet` skips matching and uses `buildSheetPrompt` (`upload-ai-sheet.ts:232`). That prompt says the garment "may be any apparel: a top, a bottom, a dress, outerwear, or anything else" (`:117`), and no Momentec template is passed. The edited sheet is a generic AI garment, not the matched style, which goes against the MoM decision to "use Momentec blank product images as shape references". Meanwhile the browser keeps the old `catalogRef` (`UploadAiDesignModal.tsx:247`), so the Lambda gets catalog data for a style the sheet no longer shows.

**Fix:** run edits through `buildCatalogProjectionPrompt` with the same template sheet as Image 1, and treat the edit note as a change to the plan, not a free redraw.

### 3.3 Only the first upload is analysed (P1)
Matching and judging use `references[0]` only (`upload-ai-sheet.ts:223`), but every reference is passed to Magnific as "Image 2, Image 3…". References arrive in drop order, so `references[0]` may be the back. Marks that only show on the other photos are never planned, and the projection prompt then tells Magnific to leave unplanned areas blank.

**Fix:** pass every reference into both Gemini calls, labelled, or ask the customer which photo is the front.

### 3.4 Uploads are downscaled to 512 px before any AI sees them (P1)
`isolateGarment` scales to 512 px before background removal (`client-image.ts:85`), and the cut-out is what gets uploaded. Gemini then reads small numbers and wordmarks from a 512 px image, and Magnific copies artwork from it. The background removal also returns a transparent PNG. Some pipelines flatten alpha to black.

**Fix:** use the low-res mask only to segment. Apply it to the full-resolution image (at least 1536 px on the long edge), then flatten onto white with `sharp` on the server before any model call.

### 3.5 Bad Gemini JSON can become a junk search query (P1)
In `describeGarment`, when JSON parses but `supported` is true and `queries` is empty, the `if` at `catalog-match.ts:258` falls through to the fallback (`:290`). The fallback takes the first six words of the raw text, which would be something like `{ "supported": true, "unsupported_reason": "",`, and searches the catalog with that. The same fallback runs on any parse failure and always sets `supported: true`.

**Fix:** use structured output (section 5.1). On failure, retry once, then fail closed with a clear error or route to an artist. Never search with raw model text.

### 3.6 Accessories are always rejected (P1)
`DESCRIBE_PROMPT` lists accessories (headband, gaiter, socks, sleeve) as supported, but `garment_piece` only allows `top | bottom | one-piece | other`. The code treats `other` as unsupported (`catalog-match.ts:250`), so a real accessory has nowhere valid to go.

**Fix:** add `accessory` to the enum and handle it in `rankCandidates`.

### 3.7 The judge falls back to the first candidate without telling anyone (P1)
If Gemini's `style` does not match a candidate, or its JSON fails to parse, the code picks `sheets[0]` (`catalog-match.ts:598, 627`) and renders it with the default plan. There is no confidence score, so "no confident match" (an MoM risk) cannot be detected or sent to an artist.

**Fix:** require `winner_style` to be an enum of the candidate styles (section 5.2), return a confidence value, and below a threshold mark the job `needs_review` instead of guessing.

### 3.8 The Lambda redraws the front and back instead of cropping them (P1)
`extractDecorations` makes two Magnific edits to "redraw only the front/back view" (`decorations.ts:203-208, 497`). The sheet already holds those views, and `splitSheet` (`upload-ai-sheet.ts:193`) can crop them deterministically. The redraw costs credits and adds a third generation, so the proof can show a garment that differs from what the customer approved.

**Fix:** crop the front and back from the sheet (port `splitSheet` to the Lambda). Use AI only if a crop fails validation.

### 3.9 Marks on the proof are AI redraws, not the customer's art (P1)
Each decoration image is a Magnific redraw of one mark (`decorations.ts:209-214`). Image models misspell words and change numbers. The proof is what the customer signs off, so this is risky.

**Fix:** ask Gemini for a bounding box per mark (it supports native `box_2d` detection) and crop from the sheet. Better still, crop from the original upload when the mark is visible there. Keep the AI redraw only as a fallback for marks that are cut off.

### 3.10 Mark size in inches is guessed by the LLM (P2)
`fit.widthIn/heightIn` come from the prompt ("print size in inches for the gender and size", `decorations.ts:134`). Gemini has no garment dimensions, so the numbers are invented and then snapped to `params`.

**Fix:** compute the size: bounding-box fraction × that style's measured panel size for the gender and size (from Momentec spec data), then snap to the location's allowed `params`.

### 3.11 The sheet split has no validation (P2)
`splitSheet` looks for the white cross. If Magnific draws across the gap, the crop boxes fall back to the midpoint with no warning (`upload-ai-sheet.ts:176`). The four views and the proof can then contain fragments of other cells.

**Fix:** the template layout is fixed (960×1280, 96/128 px gaps). Scale those boxes to the output size, then check that each cell has one garment blob not touching the edges. Retry generation once if that check fails.

### 3.12 The PDF ignores data the job already has (P1, quick win)
`index.ts:34` passes only the extracted decorations and `garmentSize` to `buildProofPdf`. `readJob` throws away the customer fields, and `catalog.style` is read but not printed. So the PDF always shows style `228435`, the sample comment, and the sample URL (`proof.ts:19-34`), although `job.json` contains the real style, name, and message.

**Fix:** pass `catalog.style`, `catalog.name`, the customer name, and the customer message into `ProofSource`. Keep the red highlight only for fields that truly have no source (REF#, ecom order#, artist), and fill those once the Comms request id is available.

### 3.13 Smaller items
- The sport filter takes the category in upper case (`catalog-match.ts:177`). Values such as `TEES`, `TOPS`, `POLOS`, `CORPORATE APPAREL`, and `BOTTOMS` are not sports, so every search runs twice. Map categories to catalog sports, or drop the filter for them.
- `queryCatalog` has no timeout (`catalog-match.ts:438`). A catalog cold start takes about 30 s, and there are up to 9 sequential searches.
- `setDefaultAutoSelectFamilyAttemptTimeout(10_000)` (`catalog-match.ts:7`) is a WSL workaround that changes networking for the whole process. Gate it on an env flag.
- `/api/upload-ai-design/match` is not called by the UI. It is still a public endpoint that spends Gemini credits. Remove it.
- The 3D path calls `waitForCreation(..., null)`, which never times out (`upload-ai-assets.ts:271`). The MCP client is never closed, and every call refreshes the OAuth token.

## 4. Prompting issues

### 4.1 No structured output, temperature, or retries (all Gemini calls)
`describeGarment`, `chooseStyleAndPlan`, and `listDecorations` call `getGenerativeModel({ model })` without `generationConfig`. So:
- Output is free text. The code strips ``` fences by hand and calls `JSON.parse`. In the Lambda, one bad response throws and fails the job (`decorations.ts:261`). Async invoke then retries the whole job twice, spending Magnific credits each time.
- Default sampling temperature means the same upload can match different styles on different runs.
- There are no timeouts.

**Fix:** set `temperature: 0` (or 0.2), `responseMimeType: "application/json"`, and a `responseSchema` on every call. Wrap each call in a retry with a timeout. The installed `@google/generative-ai@0.21` supports these options.

### 4.2 `DESCRIBE_PROMPT` (catalog-match.ts:25)
| Issue | Why it matters | Fix |
|---|---|---|
| The JSON example lists 9 logo locations and 7 text locations as values (`:44-45`) | Models copy example values. "Only include … actually visible" comes after the example and is weaker than it. | Put enums in a schema. Use empty arrays in examples. |
| Product names are hardcoded (`:27-31`) | They will drift from `products.csv` as the catalog changes, and the "do NOT put Sleeveless before…" rules patch search quirks inside the prompt. | Build the name list from the catalog at startup, or have Gemini return attributes (neck, sleeve, buttons, sport cues) and build the queries in code. |
| Location names do not match catalog names | `rankCandidates` adds score only on exact name equality (`:380-387`). If wording differs, the bonus never applies. | Use the catalog's real location names as the enum. |
| Accessory and `other` conflict | See 3.6. | Add an `accessory` value. |
| Segment is guessed from a photo | Unreliable, and the form already has gender. | Use the form value, and ask the model only when it is missing. |
| No uncertainty field | "Not sure" cannot be expressed. | Add `confidence` and `notes`. |

### 4.3 `JUDGE_AND_PLAN_PROMPT` (catalog-match.ts:51)
- **One call does two jobs.** Picking the style and writing the full plan in one response tends to make the plan weaker. At minimum, ask for a short per-candidate comparison (neckline, sleeve, placket, hem) before the winner. That improves the choice and gives an audit trail.
- **The mapping is free prose.** Lines such as `"Upper Left Chest (m6): shield crest in WHITE (#FFFFFF)…"` are later checked with `lower.includes(name)` (`colors.ts:326`). A line about an unsupported sleeve logo passes if it mentions any allowed location name anywhere in the text. A schema with `location_code` as an enum of the winner's codes rules this out.
- **Dropped marks are not recorded.** The prompt says to omit marks on unsupported places but never asks what was dropped. Artists and customers should see that ("sleeve patch omitted, not supported on style X"). Add `dropped_marks[]` and print it in the PDF comments.
- **Hex codes read from a photo are rough.** Gemini estimates hex from pixels, and the README confirms the colors are unreliable. Extract a palette in code (k-means on the masked garment pixels with `sharp`), give Gemini the swatches, and let it assign roles (body, accent, logo ink) instead of inventing hex values.
- **Customer color intent is ignored.** The MoM requires exact or PMS colors when the customer asks for them. The message field never reaches any prompt, and every color is always snapped. Add a step that reads `message` for explicit colors or PMS codes, and skip snapping for those zones.
- **No confidence score.** See 3.7.

### 4.4 `buildCatalogProjectionPrompt` (upload-ai-sheet.ts:21)
- **The left and right view text contradicts itself.** `ANGLE.left` (`:12`) says the left cell is "the side on the viewer's left in the front view" (the wearer's right side) and that "the front of the garment points toward the left edge". When you turn a garment to show the side that was on the viewer's left, its front points to the viewer's **right**. `ANGLE.right` has the mirrored mistake. Catalog locations such as "Left Short Sleeve" use the wearer's side, and the Lambda's `fromCenter` uses the wearer's side (`decorations.ts:133`). Sleeve marks can end up on the wrong sleeve. **Fix:** check which side Momentec's `preview-<style>_left` render shows, state that one convention in wearer terms ("left cell = wearer's left side"), and use it in every prompt.
- **Too long, and the rules repeat.** There are four blocks marked "Critical", CAPS "MUST" rules, the same placement rules said three ways, and per-view text. Image-edit models follow short, ordered instructions better. Keep it to: what Image 1 is, what Image 2 is, the zone and color table, the marks to apply, and the layout rules.
- **Image models do not reliably follow hex codes (verify).** Asking for `#2A0A5F` in text gives an approximate color at best. Options: (a) add a labelled swatch image as an extra reference, (b) recolor body zones after generation in code, or (c) best: check whether Momentec's own renderer (`print3d.momentecbrands.com/api/render?...texture=`) can paint zone colors directly, so AI only places artwork.
- **`quality: "low"` and `resolution: "1k"`** (`magnific.ts:303-304`). The proof is built from this output. Use a higher quality for the final sheet and keep low quality for previews only.
- **Free text from the edit box goes straight into the image prompt** (`upload-ai-sheet.ts:102`). Its scope is small, but it lets a customer ask for anything, including third-party trademarks. Screen it, or limit edits to plan changes.

### 4.5 `DECORATION_LIST_PROMPT` (lambda/src/decorations.ts:75)
- **Plan hints from the client are pasted into the prompt** (`buildCatalogContextBlock`, `:169-179`). The plan comes from the browser, so a tampered request is a prompt-injection path. The hints also push the model to list marks that are planned but not visible, which goes against "a mark counts only when … clearly visible".
- **Coordinates and inches are guessed.** See 3.9 and 3.10. Gemini's native bounding-box output is more reliable than asking for `fromTop` and `fromCenter` fractions.
- **`isEmptyMark` regex** (`:483`) drops any mark whose model-written prompt contains words like "unknown" or "no number". That is fragile. Add an explicit `visible: boolean` to the schema instead.
- **Team text is printed as `SENTINEL`** (`proof.ts:298`). Sentinel is a number height. Confirm the label for team wordmarks against the FreeStyle proof spec.

### 4.6 Color snapping
- **The Lambda never calls `/colors/nearest`.** It reads `MOMENTEC_CATALOG_SEARCH_URL` and `CATALOG_API_KEY` (`lambda/src/colors.ts:1795-1800`), but `docs/aws.md` sets only `PROOF_BUCKET`, `GEMINI_API_KEY`, and `MAGNIFIC_API_KEY` on the function. It always uses the local ΔE76 fallback. `how-it-works.html` says otherwise.
- **The palette is copied in two places** (`lib/colors.ts` and `lambda/src/colors.ts`, 173 colors each), with slightly different brand handling. Keep one source in the backend. The MoM requires PMS and CMYK to stay backend-only, so the palette should not ship in either bundle once PMS is added.
- **ΔE76 is weak for saturated colors.** Move to CIEDE2000 before customers judge color matches.
- **The hex regex** `COLOR_HEX_RE` (`lib/colors.ts:187`) also replaces up to five words before each hex with the snapped name. Words in the list such as "old", "true", "power", "soul", "storm", "baseball", and "giants" can eat ordinary words. Structured color fields remove the need for this regex.

### 4.7 No evaluation set
There is no fixed set of test uploads with expected answers. The `scratch/*.mjs` scripts are one-off visual checks. Every prompt change is judged by eye.

**Fix:** build a set of 30 to 50 real uploads covering each sport and cut, with labels for the expected style, logo and text location codes, roster marks, and zone colors. Score style top-1 and top-3 accuracy, placement precision and recall, color ΔE2000, and text spelling. Run it on each prompt or model change and record the results in the repo.

## 5. Suggested prompt structure

### 5.1 Describe, with a schema
```ts
import { SchemaType } from "@google/generative-ai";

const model = genAI.getGenerativeModel({
  model: process.env.GEMINI_MODEL ?? "gemini-2.5-flash",
  generationConfig: {
    temperature: 0,
    responseMimeType: "application/json",
    responseSchema: {
      type: SchemaType.OBJECT,
      properties: {
        supported: { type: SchemaType.BOOLEAN },
        unsupported_reason: { type: SchemaType.STRING },
        garment_piece: { type: SchemaType.STRING, enum: ["top", "bottom", "accessory", "one-piece", "other"] },
        neckline: { type: SchemaType.STRING, enum: ["crew", "v-neck", "scoop", "collar", "hood", "button-placket", "zip", "none"] },
        sleeves: { type: SchemaType.STRING, enum: ["sleeveless", "short", "3/4", "long", "none"] },
        has_buttons: { type: SchemaType.BOOLEAN },
        queries: { type: SchemaType.ARRAY, items: { type: SchemaType.STRING } },
        visible_marks: {
          type: SchemaType.ARRAY,
          items: {
            type: SchemaType.OBJECT,
            properties: {
              kind: { type: SchemaType.STRING, enum: ["logo", "team_text", "number", "name"] },
              placement: { type: SchemaType.STRING, enum: CATALOG_LOCATION_NAMES }, // built from locations.json
              text: { type: SchemaType.STRING },
            },
            required: ["kind", "placement"],
          },
        },
        confidence: { type: SchemaType.NUMBER },
      },
      required: ["supported", "garment_piece", "sleeves", "queries", "visible_marks", "confidence"],
    },
  },
});
```

### 5.2 Judge and plan, with enums per request
Build the schema in code for each call so that:
- `winner_style` is an enum of the candidate style numbers, plus `"none"`.
- `color_zones[].zone_code` is an enum of the winner's `color_zones[].code`. Since the winner is not known in advance, use the union of all candidates' codes and filter afterwards, or split into two calls: judge, then plan.
- `logos[].location_code` and `texts[].location_code` are enums of the non-legacy codes.
- `texts[].content` holds the exact string, and `texts[].height_in` is an enum of that location's `params`.
- `dropped_marks[]` holds `{ description, observed_placement, reason }`.
- `candidate_review[]` holds `{ style, neckline_match, sleeve_match, placket_match, hem_match }` (0 to 1).
- `confidence` is 0 to 1.

Then **build the Magnific prompt in code from these fields.** Gemini should never write prose that goes to the image model unchecked. `filterPlanToAllowedCatalog` and the hex regex can then be removed.

### 5.3 Add a check after rendering
After Magnific returns, make one Gemini call that receives the plan and the rendered sheet. It answers per planned mark (present, correct location, text spelled exactly) and reports any extra mark. If it fails, regenerate once with the error added to the prompt. If it fails again, mark the job `needs_review`. This catches misspelled names and numbers and stray logos before a customer sees them.

### 6.1 Security
| # | Issue | Where | Fix |
|---|---|---|---|

### 6.2 Operations
- **Production code is not version controlled.** `.gitignore:27-28` ignores `lambda/` and `Momentec_VectorEmbeddings/`, and `git ls-files` lists neither. The deployed Lambda cannot be rebuilt from git. Commit both, or move them to their own repos. Keep `dist/` and `node_modules/` ignored.
- **Lambda retries are not idempotent.** Async invoke retries a failed job twice by default. Each retry runs every Magnific edit again. Set `MaximumRetryAttempts` to 0 and handle retries per step, or skip work when `status.json` is already `done`. Add an on-failure destination (an SQS DLQ) and an alarm.
- **The 15-minute limit is a real risk.** Each Magnific poll can wait up to 300 s (`GPT_EDIT_POLL_MS`), and there are two sequential waves plus Gemini. A slow Magnific day goes over 15 minutes. The MoM already asks whether Lambda alone is enough. Use Step Functions with one state per stage and a map state for marks.
- **Nobody watches the result.** The app user cannot read `status.json` or `proof.pdf`, nothing notifies anyone, and the Comms update is not built. Add the Comms callback, plus an alert on `failed`.
- **The deploy script is out of date.** `scripts/create-aws-proof.sh` forces `us-east-1` and `nodejs20.x`. The live setup is `ap-southeast-2` and Node 24. Fix or delete it, and add a repeatable deploy (SAM, CDK, or Terraform) for both functions, the bucket, IAM, and the DLQ.
- **Data retention.** The bucket holds names, emails, and customer images with no lifecycle rule. Add SSE (check whether it is already on), a retention period, and use the MoM's proof-storage naming convention instead of `<uuid>/`.
- **Observability.** Logs are plain `console.log` strings. Use structured JSON logs with `jobId` on every line. Record the latency and cost of each Gemini and Magnific call, and store the prompt version and model id in `job.json` so you can debug a proof later.
- **Tests and CI.** There are `lib/mark-measure.test.ts` and `proof-job.check.ts`, but no test runner script and no CI. Add `typecheck`, a unit test run, and the eval set (4.7) to CI.

### 6.3 Target production flow (from the MoM)
The MoM says the POC modal will not ship and the AI Creator form stays. That changes where things run. **Everything after form submit should be one backend job.** The customer never sees the four views, so `/generate` should not be a synchronous browser call.

```
AI Creator form submit (creates Comms mock-up request)
  → POST /proof-jobs  {commsRequestId, photo(s), gender, size, category, message}
      (authenticated server-to-server; idempotency key = commsRequestId)
  → S3: original upload + job.json
  → Step Functions:
      1 normalize image (full-res mask, flatten on white, strip EXIF)
      2 describe (schema)            → unsupported → Comms "artist review"
      3 catalog search + template fetch (cache templates in S3 by style)
      4 judge + plan (schema, confidence)  → low confidence → artist review
```
